# 1.2 — Refresh token rotation & oturum iptali

> Faz 1, adım 1.2'nin çıktısı. `refresh_tokens` tablosu, httpOnly cookie,
> her kullanımda rotasyon, yeniden kullanım (reuse) tespiti, logout ve
> **gerçek veritabanına karşı koşan ilk testler**.

## 1. Neden refresh token

Access token 15 dakika yaşıyor ve doğrulanırken veritabanına BAKILMIYOR —
hızlı, ama bu yüzden iptal de edilemiyor. Uzun oturum ve "oturumu kapat"
yeteneği bu adımda geliyor: uzun ömürlü, veritabanında tutulan, her
kullanımda değişen bir refresh token.

## 2. Token'ın kendisi

`internal/auth/refresh.go` — 32 byte `crypto/rand`, base64url ile 43
karakter.

- **JWT DEĞİL, opak rastgele değer.** Refresh token'ın iptal edilebilir
  olması gerekiyor (logout, reuse), bu da her kullanımda veritabanına bakmak
  demek. Veritabanına zaten bakılıyorsa imza hiçbir şey kazandırmaz; sadece
  fazladan bir doğrulama yüzeyi (alg confusion, "süresi dolmamış ama iptal
  edilmiş" ayrımı) eklerdi.
- **Veritabanında ham token değil, HMAC-SHA256 özeti var.** Veritabanı
  dökümü ele geçse bile satırlardan kullanılabilir token üretilemiyor;
  anahtar (`REFRESH_TOKEN_SECRET`) veritabanında değil.
- **Argon2 kullanılmıyor** (parolalardan farkı burada): token 256 bit
  rastgele, sözlük saldırısına konu olacak düşük entropili bir sır değil.
  Yavaş özet güvenlik katmaz, yalnızca her yenilemeyi pahalılaştırırdı.

Ortam değişkeni `JWT_REFRESH_SECRET` **değil `REFRESH_TOKEN_SECRET`**:
refresh token bir JWT olmadığına göre bu anahtar da imzalama değil, HMAC
anahtarı. Yanlış ön ek kodu 6 ay sonra okuyanı yanıltırdı. Ömür:
`REFRESH_TOKEN_TTL`, varsayılan 30 gün (access TTL'den uzun olmak zorunda,
yapılandırma bunu doğruluyor).

## 3. Şema

`db/migrations/00003_refresh_tokens.sql`:

| Sütun        | Not                                              |
| ------------ | ------------------------------------------------ |
| `id`         | uuid PK                                          |
| `session_id` | rotasyon zinciri = oturum **ailesi**             |
| `user_id`    | `users(id)` FK, `ON DELETE CASCADE`              |
| `token_hash` | `bytea` UNIQUE — HMAC-SHA256                     |
| `issued_at`  |                                                  |
| `expires_at` |                                                  |
| `used_at`    | rotasyonda dolar; ikinci kez sunulması = reuse   |
| `revoked_at` | logout veya reuse tespiti                        |

İndeksler: `session_id` (aile iptali), `user_id` (cascade silme indekssiz
tam tarama yapardı), `expires_at` (budama — Faz 3'te worker'a verilecek).

## 4. Rotasyon ve reuse tespiti

`internal/sessions/service.go`. `Rotate` tek bir transaction içinde:

1. `SELECT … WHERE token_hash = $1 **FOR UPDATE**`
2. satır yok → `ErrInvalidRefreshToken`
3. `revoked_at` dolu → `ErrInvalidRefreshToken` (oturum zaten kapalı)
4. **`used_at` dolu → ailenin tamamı iptal edilir**, `commit`,
   `ErrRefreshTokenReused` (uyarı loglanır)
5. süresi geçmiş → `ErrInvalidRefreshToken`
6. aksi hâlde: satır `used_at` ile işaretlenir, **aynı `session_id`** ile
   yenisi yazılır, `commit`

**`FOR UPDATE` neden şart:** aynı token'la eş zamanlı gelen iki istek bu
satırda sıraya giriyor; ikincisi kilidi aldığında `used_at` dolmuş oluyor ve
reuse olarak işleniyor. Kilit olmasaydı ikisi de geçerli sayılır, aynı
aileden iki paralel zincir doğardı.

**Neden ailenin tamamı iptal ediliyor:** kullanılmış bir token'ın tekrar
sunulmasının iki açıklaması var — token çalındı, ya da meşru istemcide eski
kopya kaldı. İkisini ayırt etmek mümkün değil; güvenli taraf seçiliyor,
kullanıcı yeniden giriş yapıyor.

**Bilinçli bedel:** iki sekme aynı anda yenileme yaparsa oturum düşer.
Yaygın çözüm "birkaç saniyelik tolerans penceresi" ama bu, çalınan bir
token'a da aynı pencereyi açıyor. 15 dakikalık access token ile yenileme
seyrek olduğu için katı davranış seçildi.

## 5. HTTP tarafı

| Uç                       | Sonuç                                                    |
| ------------------------ | -------------------------------------------------------- |
| `POST /v1/auth/register` | 201 + access token (gövde) + refresh cookie              |
| `POST /v1/auth/login`    | 200 + access token + refresh cookie                      |
| `POST /v1/auth/refresh`  | 200 + YENİ access token + YENİ cookie                    |
| `POST /v1/auth/logout`   | **204**, oturum ailesi iptal, cookie silinir             |

Cookie: `uptime_refresh`, `HttpOnly`, `SameSite=Strict`,
`Path=/v1/auth`, `Secure` **yalnızca üretimde**.

- **HttpOnly:** JavaScript okuyamıyor; XSS ile token dışarı sızmıyor.
- **Path=/v1/auth:** refresh token her API isteğinde ağda dolaşmıyor.
- **SameSite=Strict:** cookie'yi taşıyan tek uç yenileme/çıkış olduğu için
  başka bir sitenin tetiklediği istekte gönderilmemesi CSRF'i kapatıyor.
  Frontend (:3100) ile api (:3400) aynı site sayıldığından meşru akış
  etkilenmiyor.
- **Secure sadece üretimde:** local geliştirme http üzerinden koşuyor,
  Secure cookie orada hiç gönderilmezdi.
- **Access token cookie DEĞİL, gövdede:** istemcinin belleğinde duruyor,
  tarayıcı onu kendiliğinden hiçbir isteğe eklemiyor — API çağrılarında CSRF
  diye bir konu doğmuyor.

**Hata cevabı tek:** tanınmayan, süresi dolmuş, iptal edilmiş ve yeniden
kullanılmış token'ların hepsi `401 invalid_refresh_token` +
"oturum geçersiz, yeniden giriş yapın" alıyor ve cookie temizleniyor.
Reuse'u ayrı bir kodla bildirmek, token'ı çalana "yakalandın" demekten başka
işe yaramazdı; meşru istemcinin yapacağı şey her hâlükârda aynı. Ayrım
**sunucu logunda** duruyor (`WARN … oturum iptal edildi`).

**Logout her zaman 204**, cookie olmasa da: "bu token sistemde yok" bilgisi
vermenin faydası yok, çıkışın etkisi zaten aynı.

## 6. Testler — ilk gerçek veritabanı testleri

`internal/sessions` testleri **gerçek Postgres'e** karşı koşuyor. Gerekçe:
burada ölçülen şey (satır kilidi, transaction sınırları, eş zamanlı iki
yenilemeden yalnızca birinin kazanması) sahte bir store ile ölçülemez —
sahte store'a bu davranışı ben yazardım ve test kendi kopyasını doğrulamış
olurdu.

- Testler **ayrı bir veritabanında** (`<db>_test`) koşuyor, onu kendileri
  oluşturup goose migration'larını uyguluyor; geliştirme verisi silinmiyor.
- `DATABASE_URL` yoksa **atlanıyorlar** (yerelde veritabanı olmadan da
  `go test ./...` yeşil kalsın), **CI'da ise her zaman tanımlı**.
- **CI'a Postgres servisi eklendi.** 0.4'te "gerçek ihtiyaç doğduğunda
  eklenecek" denmişti; ihtiyaç bu adımda doğdu.

Kapsam: oturum açma (ham token saklanmıyor), rotasyon (aynı aile, yeni
değer), bilinmeyen/süresi geçmiş token, **reuse → ailenin tamamı iptal**,
**eş zamanlı iki yenilemeden yalnızca biri kazanıyor**, logout, idempotent
logout, kullanıcılar arası izolasyon.

HTTP tarafı (cookie bayrakları, durum kodları, hata gövdesi) sahte bir
servisle `internal/httpapi` içinde ölçülüyor — orada konu iş mantığı değil,
sözleşme.
