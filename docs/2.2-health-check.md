# 2.2 — Tek seferlik health check

> Bir monitor'ü "şimdi kontrol et": gerçek HTTP isteği, ölçülen yanıt süresi
> ve **hata tiplerinin ayrı ayrı sınıflandırılması**. Kontrol mantığı ağ
> bağımlılığı olmadan test edilebilir.

## 1. Paket sınırı

`internal/checker` — girdisi bir **hedef**, çıktısı tek bir **sonuç**.

Bilmediği şeyler bilinçli: zamanlama (3.2), durum makinesi (3.3), saklama
(2.3). Bu yüzden aynı kodu hem manuel uç hem de 3.2'nin worker'ı çağırabiliyor
— kontrolün "ne zaman" çalıştığı sorusu çağıranın, "ne oldu" sorusu bu paketin.

```go
type Target struct {
    URL     string
    Method  store.MonitorMethod
    Timeout time.Duration
    ExpectedStatusMin, ExpectedStatusMax int32
    DegradedAfter time.Duration // 0 = "yavaş" sinyali kapalı
}

func (c *Checker) Run(ctx context.Context, target Target) (Result, error)
```

## 2. En önemli ayrım: "başarısız kontrol" ≠ "kontrol yapılmadı"

`Run` yalnızca kontrol **hiç çalışamadığında** hata döndürüyor
(`ErrCheckNotRun`); hedefin cevap vermemesi hata değil, **başarısız bir
sonuç**.

| Durum                                  | Dönen                                    |
| -------------------------------------- | ---------------------------------------- |
| Hedef 500 döndü / zaman aşımına uğradı  | `Result{Outcome: failure, …}`, hata `nil` |
| Çağıranın context'i iptal edildi        | `ErrCheckNotRun`, sonuç YOK               |

Ayrım `ctx.Err()`'e bakarak yapılıyor: kendi son tarihimiz (monitor'ün
`timeout_ms`'i) dolduysa bu bir **ölçüm**; çağıranın context'i düştüyse ölçüm
**yokluğu**.

**Neden bu kadar önemli:** 3.2'de worker kapanırken devam eden kontroller
iptal edilecek. İptali "başarısız kontrol" saymak, her yeniden başlatmada
sahte bir kesinti kaydı ve 4.1'de **gerçek olmayan bir incident** demekti.
Kural bu adımda, ilk kullanıcısından önce kuruldu ve testi var.

## 3. Hata sınıflandırma — metin değil TİP

```go
switch {
case errors.Is(err, context.DeadlineExceeded): → timeout
case isDNSError(err):                          → dns
case isTLSError(err):                          → tls
case isConnectionRefused(err):                 → connection_refused
case isTimeout(err):                           → timeout
default:                                       → unknown
}
```

`strings.Contains(err.Error(), "refused")` **yapılmıyor**: hata metinleri Go
sürümüne ve işletim sistemine göre değişiyor. Sınıflandırma `errors.As` /
`errors.Is` ile tipler üzerinden ve sarmalayıcıların (`url.Error` →
`net.OpError` → `os.SyscallError`) içine bakarak çalışıyor.

| Sınıf                | Nasıl tanınıyor                                                                                     |
| -------------------- | --------------------------------------------------------------------------------------------------- |
| `timeout`            | `context.DeadlineExceeded` · `net.Error.Timeout()`                                                    |
| `dns`                | `*net.DNSError`                                                                                       |
| `tls`                | `*tls.CertificateVerificationError` · `tls.RecordHeaderError` · `tls.AlertError` · `x509.*` · `http.ErrSchemeMismatch` |
| `connection_refused` | `syscall.ECONNREFUSED` **veya** Winsock 10061                                                          |
| `unexpected_status`  | cevap alındı, beklenen aralığın dışında                                                                |
| `unknown`            | geri kalan (yönlendirme sınırı, kopan bağlantı, protokol hatası)                                       |

**Sıralama kararları:**

- **DNS zaman aşımı `dns` sayılıyor, `timeout` değil**: sorun hedefin yavaş
  olması değil, adının çözülememesi. Kullanıcının yapacağı iş farklı.
- **`http.ErrSchemeMismatch` (https istendi, düz http cevabı geldi) `tls`**:
  hata TLS katmanına ulaşmadan net/http tarafından yakalanıyor ama
  kullanıcının sorunu tam olarak "bu port TLS konuşmuyor".
- **`blocked_url` bu paketten ASLA çıkmaz** — testi var. O, isteği hiç
  göndermeyen SSRF korumasının (7.4) sonucu; buradaki kod isteği çoktan
  göndermiş oluyor.

### Testin yakaladığı gerçek hata: Windows'ta `connection_refused`

`errors.Is(err, syscall.ECONNREFUSED)` geliştirme makinesinde **çalışmıyor**:
Windows soket hatalarını Winsock numaralarıyla (10061) döndürüyor ve bu sabit
`syscall.ECONNREFUSED` ile eşleşmiyor. Kapalı bir loopback portuna yapılan
test bunu ilk koşuda yakaladı — hata `unknown` olarak sınıflanıyordu. Linux
konteynerinde çalışıp geliştirme makinesinde sessizce yanlış sınıflandıran bir
davranış, testsiz asla fark edilmezdi.

## 4. İstemci: paylaşılan ama sınırlı

`http.DefaultClient` **kullanılmıyor** (zaman aşımı yok, yönlendirme sınırı
10, global olduğu için başka bir paketin ayarı bizimkini etkileyebilir).

| Ayar                        | Karar                     | Gerekçe                                                                                                       |
| --------------------------- | ------------------------- | ------------------------------------------------------------------------------------------------------------- |
| Bağlantı yeniden kullanımı  | **KAPALI**                | Havuzdan gelen bağlantı el sıkışmayı atlar; aynı monitor "200 ms / 40 ms" gibi karşılaştırılamaz bir seri üretirdi. Ayrıca her kontrol yolun tamamını sınıyor |
| Zaman aşımı                 | `context`, `client.Timeout` değil | Monitor başına farklı ve çağıranın iptali aynı mekanizmadan geçiyor              |
| Yönlendirme                 | en fazla **5**            | Döngü, isteği zaman aşımına kadar meşgul ederdi                                                                |
| Gövde                       | en fazla **64 KiB**, okunup atılıyor | İçerik kullanılmıyor ama **okunuyor**: başlığı anında gönderip gövdede takılan servis sağlıklı değil |
| Proxy                       | ortam değişkenleri **okunmuyor** | Aradaki bir proxy'nin önbelleği "servis ayakta" yanılgısı üretebilir                                     |
| User-Agent                  | `uptime-mini/1.0 (+repo)` | Hedefin loglarında kim olduğumuz görünsün                                                                       |

> ⚠️ **SSRF (7.4) ve yönlendirme:** yönlendirme, URL doğrulamasını atlamanın
> klasik yolu — dış görünen bir adres `169.254.169.254`'e yönlendirebilir.
> 7.4'ün kontrolü ilk URL'e değil **her durağa** uygulanmalı; yeri
> `CheckRedirect`'in içinde işaretli.

## 5. Sonuç ve `degraded`

```go
type Result struct {
    Outcome      store.CheckOutcome    // success | degraded | failure
    HTTPStatus   int32                 // 0 = cevap hiç alınamadı
    ResponseTime time.Duration
    ErrorType    store.CheckErrorType  // "" = hata yok
    ErrorMessage string
    CheckedAt    time.Time
}
```

Karar sırası: **önce status, sonra hız**. Beklenmeyen bir status hızlı
geldiyse bu onu başarılı yapmaz (testi var).

`degraded` "çalışıyor ama yavaş" demek ve **hata değil** — 0.1'in uptime
tanımında DEGRADED "up" sayılıyor. Karar kontrol anında veriliyor, sonradan
eşikten türetilmiyor: eşik değişince geçmiş veri anlamını değiştirirdi.

### Yeni sütun: `degraded_response_ms` (migration 00006)

2.1'in kuralı gereği burada geldi — yazma yoluna sahip olan adım bu.

- **NULL = yavaşlık sinyali kapalı**, varsayılan da NULL. "Makul" gecikme
  hedefe göre değişir; uydurulmuş bir varsayılan kullanıcının hiç istemediği
  `degraded` kayıtları üretirdi.
- Şemada `CHECK (degraded_response_ms IS NULL OR BETWEEN 1 AND timeout_ms)`:
  **zaman aşımından büyük bir eşik ulaşılamaz** olurdu (daha yavaş cevap
  zaten timeout'a takılır) — yani sessiz bir yapılandırma hatası.
- PATCH'te **üç durumlu**: alan gönderilmedi (dokunma) · `null` (eşiği
  kaldır) · sayı. Tek işaretçi ilk ikisini ayıramadığı için `nullable[T]`
  tipi eklendi (`UnmarshalJSON` çağrıldı mı bilgisini kullanıyor).

## 6. Manuel kontrol ucu

`POST /v1/orgs/{orgID}/monitors/{monitorID}/check` → **200** + sonuç.

- **Sonuç SAKLANMIYOR.** Kalıcı zaman serisine yazmak ayrı bir karar
  ("manuel kontroller uptime yüzdesini etkilemeli mi?") ve o karar 2.3'te.
- **Kontrolün başarısız olması isteğin başarısız olması değil:** "hedef
  çöktü" başarıyla üretilmiş bir cevaptır. 5xx döndürmek istemciye kendi
  hatamız gibi görünürdü. Kontrol hiç çalışmadıysa **503 `check_not_run`**.
- **Hedef yalnızca MONİTOR KAYDINDAN kuruluyor**; istemci gövdede URL/timeout
  geçemiyor. Geçebilseydi bu uç "istediğim adrese istek attır" hâline gelirdi.
- **Yetki: admin+ (okuma değil).** Bu uç sunucuyu dışarıya istek attırıyor —
  salt-okunur bir pano işlemi değil, tetiklenen bir yan etki. (Karşı görüş
  kayda değer: nöbetçi mühendis senaryosunda `member` da "şimdi kontrol et"
  demek isteyebilir. 0.1 §2 `member`'ı salt-okunur tanımladığı için sıkı
  taraf seçildi; genişletmek daraltmaktan kolay.)
- Hız sınırlama (7.4) bu ucun doğrudan konusu: kimlik doğrulanmış bir
  kullanıcı, sunucuyu istediği hedefe istek atmaya zorlayabiliyor.

Cevap gövdesi (süre **milisaniye**; `time.Duration` JSON'da nanosaniye olurdu):

```json
{"check":{"outcome":"failure","httpStatus":null,"responseTimeMs":2001,
          "errorType":"timeout","errorMessage":"hedef zamanında cevap vermedi",
          "checkedAt":"2026-08-12T12:03:04Z"}}
```

Cevap alınamadıysa `httpStatus` **null** — 0 uydurulmuyor.

## 7. Testler ağ olmadan

- **Uçtan uca (`httptest`)**: başarı, beklenen aralık (401 bekleyen monitor),
  degraded, zaman aşımı, kapalı port, kendi imzalı sertifika, https↔http
  karışması, yönlendirme (izleme + döngü), 256 KiB gövde, HEAD, iptal,
  bağlantıların yeniden kullanılmadığı.
- **Saf sınıflandırma**: gerçek hata DEĞERLERİ (`net.DNSError`,
  `os.SyscallError`, `x509.*`, `tls.*`) üretimdeki gibi sarmalanmış hâlde
  veriliyor. DNS dalını uçtan uca denemek gerçek bir isim sorgusu, yani ağ
  bağımlılığı isterdi.
- **Uç testleri**: sahte çalıştırıcıyla yetki/sözleşme; ayrıca gerçek
  `Checker` + gerçek `httptest` hedefiyle bir kez de bütün zincir.

**Gerçek konteynerde** (migration `version=6`), altı sınıfın hepsi gerçek ağ
davranışıyla:

| Hedef                              | outcome    | httpStatus | errorType            |
| ---------------------------------- | ---------- | ---------- | -------------------- |
| `http://localhost:3400/health`     | success    | 200        | —                    |
| `http://localhost:3400/yok…`       | failure    | 404        | `unexpected_status`  |
| `http://localhost:9`               | failure    | null       | `connection_refused` |
| `http://…-yok.invalid/`            | failure    | null       | `dns`                |
| `https://localhost:3400/health`    | failure    | null       | `tls`                |
| `http://10.255.255.1/` (2 sn)      | failure    | null       | `timeout` (2001 ms)  |
| eşik 1 ms ile `/health`            | **degraded** | 200      | —                    |

Ayrıca: `member` rolü kontrolü tetikleyemedi (**403**), tokensiz **401**;
`PATCH {"degradedResponseMs":null}` eşiği kaldırdı ve aynı monitor tekrar
`success` oldu; eşik > zaman aşımı **422** (`"zaman aşımından büyük olamaz"`);
doğrulama atlanıp doğrudan SQL yazıldığında **veritabanı reddetti**
(`monitors_degraded_response_ms_check`).

> Not: kendi `/health` ucunu kontrol edebilmek aynı zamanda **canlı bir SSRF
> örneği** — sunucu, kullanıcının yazdığı adrese kendi ağından istek atıyor.
> 7.4'ün neden atlanamaz olduğunu gösteren en somut kanıt bu satır.
