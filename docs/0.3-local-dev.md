# 0.3 — Local Geliştirme Ortamı

> Hedef (docs/0.0-constraints.md §3): GitHub'dan klonlayan biri —
> örneğin bir mülakatçı — **hiçbir dış hesap, API anahtarı veya ödeme
> olmadan** projeyi ayağa kaldırabilmeli.

## 1. Kurulum

```bash
cp .env.example .env     # olduğu gibi çalışır, düzenlemeye gerek yok
docker compose up -d     # postgres + migration + api + worker
pnpm install && pnpm dev # web (:3100), hot reload ile host'ta
```

Doğrulama:

```bash
curl http://localhost:3400/health   # {"status":"ok",...}
curl http://localhost:3400/ready    # {"status":"ready","checks":{"database":"ok"}}
```

Geliştirirken backend'i konteyner yerine host'ta çalıştırmak (daha hızlı
yeniden derleme) için:

```bash
docker compose up -d postgres   # sadece veritabanı
pnpm db:migrate                 # şemayı uygula
pnpm dev:api                    # :3400
pnpm dev:worker                 # ayrı bir terminalde
```

## 2. Servisler

| Servis | Ne yapar | Not |
|---|---|---|
| `postgres` | PostgreSQL 16 | Host'ta **5433** portunda (5432 başka bir projeye ait olabilir) |
| `migrate` | goose ile şemayı uygular, çıkar | Tek seferlik; api/worker ondan sonra başlar |
| `api` | HTTP API (:3400) | `/health` (liveness) + `/ready` (readiness) |
| `worker` | Arka plan süreci | api'ye **bağımlı değil**, ayrı ayrı yeniden başlatılabilir |

**Redis yok** — zamanlama Postgres'in `FOR UPDATE SKIP LOCKED` mekanizmasıyla
yapılacak (bkz. `docs/0.2-tech-stack.md` §5). Kullanılmayan bir altyapı
servisi taşımıyoruz; canny-mini'de Redis beş faz boyunca boş durmuştu.

## 3. Alınan kararlar

### Migration'lar ayrı bir binary'de (`cmd/migrate`), api açılışında değil

api veya worker başlarken migration çalıştırsaydı: (1) iki süreç aynı anda
kalktığında ikisi de şema değiştirmeye çalışırdı, (2) "uygulama başlarken
şemayı değiştirmek" geri alınması zor bir davranış olurdu. Compose'da
`migrate` servisi tek seferlik çalışıyor; api ve worker
`service_completed_successfully` koşuluyla onu bekliyor.

Migration dosyaları **binary'nin içine gömülü** (`go:embed`). İmaja ayrıca
SQL kopyalamak, imaj ile migration'ların sürümünün ayrışması riskini
doğururdu; gömülü olunca "bu binary hangi migration'ları biliyor" sorusunun
tek bir cevabı var.

### `/health` ve `/ready` ayrı uçlar

- **`/health` (liveness)** — süreç ayakta mı? Veritabanına **bakmaz**.
- **`/ready` (readiness)** — istek karşılayabilir mi? Veritabanını yoklar,
  ulaşılamıyorsa **503** döner.

Ayrımın sebebi somut: veritabanı düştüğünde `/health` de hata verseydi
orkestratör api'yi yeniden başlatırdı — bu veritabanını geri getirmez, sadece
kesintiyi uzatır. Doğru davranış, süreci ayakta tutup "şu an trafik alamam"
demek. Compose'daki healthcheck bu yüzden `/health` kullanıyor.

Bu davranış hem birim testlerinde (veritabanı düşükken `/health` 200,
`/ready` 503) hem gerçek konteynerlerde doğrulandı (bkz. §5).

### Veritabanına açılışta ulaşılamaması ölümcül değil

api ve worker bağlantı havuzunu kuruyor, bir kez yokluyor ve **başarısız
olsa bile çalışmaya devam ediyor** (uyarı loglayarak). Gerekçe: başlatma
sırasına bağlı çökme döngüleri yerine, hazır olmama durumunun `/ready`
üzerinden bildirilmesi. Veritabanı geri geldiğinde havuz kendiliğinden
toparlanıyor — bu da gerçekten test edildi.

### `.env` en zayıf yapılandırma kaynağı

`config.LoadDotEnv()` repo kökündeki `.env`'i arayıp yüklüyor ama **tanımlı
olan ortam değişkenlerinin üzerine yazmıyor**. Yani Docker Compose ve CI
kendi değerlerini geçtiğinde `.env` onları gölgeleyemiyor. Dosya yoksa
sessizce geçiliyor (CI'da `.env` yok).

### Sır olan ve olmayan ayrımı

`.env.example` **olduğu gibi çalışır** — ama içindeki veritabanı şifresi
gerçek bir sır değil: yalnızca local Docker ağındaki bir Postgres'e erişiyor.
Buna karşılık JWT imzalama anahtarları `__GENERATE_ME__` olarak duruyor ve
Faz 1'de uygulama bu değerlerle **boot etmeyi reddedecek**.

Gerekçe canny-mini'de yaşandı: `.env.example` bir zamanlar ÇALIŞAN placeholder
sırlar taşıyordu; bilinen bir JWT anahtarı = tam kimlik taklidi demek.
"Klonlayan herkes çalıştırabilsin" hedefi, "imzalama anahtarları tahmin
edilebilir olsun" anlamına gelmiyor.

### Portlar

| | uptime-mini | canny-mini |
|---|---|---|
| web | 3100 | 3000 |
| api | 3400 | 3333 |
| postgres (host) | 5433 | 5432 |

İki proje aynı makinede aynı anda çalışabiliyor. 0.2'de bu çakışma gerçekten
yaşandı (tarayıcı yanlış projenin sayfasını gösterdi).

## 4. Faydalı komutlar

```bash
pnpm db:migrate     # şemayı uygula (goose up)
pnpm db:status      # hangi migration'lar uygulanmış
pnpm db:down        # son migration'ı geri al
pnpm go:test        # backend testleri
pnpm go:lint        # go vet + gofmt kontrolü
docker compose logs -f api worker
docker compose down -v   # her şeyi sil (veri dahil)
```

Yeni migration eklemek: `backend/db/migrations/` altına `00002_<ad>.sql`
oluştur, içine `-- +goose Up` / `-- +goose Down` bölümlerini yaz.

## 5. Doğrulama (bu adımda gerçekten yapıldı)

- `docker compose up -d --build` → postgres **healthy**, migrate **exited 0**
  (`version=1`), api **healthy**, worker **up**.
- Şema gerçekten uygulandı: `psql` ile 7 enum tipi (`org_role`,
  `monitor_status`, `monitor_method`, `check_outcome`, `check_error_type`,
  `incident_status`, `incident_impact`) ve `goose_db_version` tablosunda
  `version_id = 1` görüldü.
- `GET /health` → 200, `GET /ready` → 200 (`database: ok`).
- **`docker compose stop postgres` sonrası:** `/health` hâlâ **200**,
  `/ready` **503** (`database: unreachable`), api konteyneri **healthy**
  kalmaya devam etti (yeniden başlatılmadı) — yani ayrımın amacı çalışıyor.
- `docker compose start postgres` sonrası `/ready` ilk denemede tekrar
  **200** döndü (havuz kendini toparladı).
- Host'tan `pnpm db:status` konteynerdeki veritabanına 5433 üzerinden
  bağlandı ve `version=1` bildirdi — yani `.env` yükleme yolu da çalışıyor.
- `gofmt -l` boş, `go vet` temiz, `go test ./...` 3 paket yeşil (18 test).
