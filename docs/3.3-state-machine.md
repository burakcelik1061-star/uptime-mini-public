# 3.3 — Durum makinesi (UP/DOWN/DEGRADED)

> Monitor'ün durumu artık TEK bir kontrol sonucuna değil ARDIŞIK sonuçlara
> bakılarak belirleniyor: N ardışık hatadan sonra DOWN, M ardışık yanıttan
> sonra tekrar UP. Karar **saf bir fonksiyonda** (`monitors.NextState`) ve
> eşikler monitor bazında ayarlanabiliyor.

## 1. Saf fonksiyon: `monitors.NextState`

```go
type State struct {
    Status               store.MonitorStatus
    ConsecutiveFailures  int32
    ConsecutiveSuccesses int32
    FailureThreshold     int32
    RecoveryThreshold    int32
}

func NextState(current State, outcome store.CheckOutcome) Transition
```

Girdisi bir durum + bir sonuç, çıktısı yeni durum + `Changed` bayrağı.
Veritabanı, saat ve ağ GÖRMÜYOR. Bu, adımın şartıydı ve pratik karşılığı şu:
"5 ardışık hata, sonra 1 başarı, sonra kurtarma" gibi senaryolar gerçek zamanı
beklemeden tek satırda test edilebiliyor (`state_test.go` bunu böyle yapıyor).
Yan etkiler (yazma, loglama) çağıranda — `internal/scheduler`.

### Kurallar

| Sonuç | Sayaçlar | Durum |
| --- | --- | --- |
| `failure` | hata +1, başarı 0 | Sayaç **eşiğe ULAŞTIĞINDA** `down`; öncesinde durum DEĞİŞMEZ |
| `success` | başarı +1, hata 0 | `down` ise kurtarma eşiği kadar ardışık yanıt gerekiyor; değilse `up` |
| `degraded` | başarı +1, hata 0 | `down` ise kurtarma eşiğinden sonra `degraded`; değilse hemen `degraded` |

**Flapping önlemenin özü:** tek bir kayıp paket kesinti ilan etmiyor, tek bir
başarılı cevap da kesintiyi bitirmiyor. Araya giren tek bir başarı hata
sayacını sıfırlıyor — sıfırlanmasaydı gürültülü bir servis günün sonunda
mutlaka DOWN olurdu.

**Neden DEGRADED eşiğe tabi değil (bilinçli asimetri):** "yavaş" bir kesinti
iddiası değil — incident açmıyor (4.1 `down`a bakacak) ve zaten kontrol anında
karara bağlanmış bir ölçüm (0.1 §5). Eşiğe bağlamak üçüncü bir eşik, "yavaşlık
ne zaman biter" için de dördüncü bir kural demekti. Kesinti kararı ise pahalı
olduğu için eşikli.

**`pending` ilk YANITTA `up`:** kurtarma eşiği "kesintiden çıkış" kuralı, "ilk
kez ölçüldü" değil. Yeni eklenen bir monitor'ün iki tur boyunca `pending`
görünmesi, kullanıcının gözünde ürünün çalışmaması demekti. Ama ilk kontrol
BAŞARISIZSA eşik yine geçerli: yanlış yazılmış tek bir URL anında kesinti
üretmiyor.

**`paused` monitor'e dokunulmuyor:** duraklatılmış monitor zaten zamanlanmıyor
(3.2); buraya ancak kullanıcı kontrol sürerken duraklattıysa gelinir ve o
kararı ezmek yanlış olurdu. Yazma sorgusu AYRICA `is_active` şart koşuyor
(§3) — aynı yarış iki katmanda kapalı.

**Bozuk eşikler kırpılıyor:** şema 1-10 zorluyor, yani üretimde 0 gelmemeli.
Yine de saf fonksiyon 0'ı varsayılana, 999'u üst sınıra çekiyor: sıfır bir eşik
"ilk kontrolde down" gibi sessiz ve tuhaf bir davranış üretirdi.

## 2. Şema

`db/migrations/00009_monitor_state.sql`

```sql
ALTER TABLE monitors
    ADD COLUMN consecutive_failures  integer NOT NULL DEFAULT 0 CHECK (… >= 0),
    ADD COLUMN consecutive_successes integer NOT NULL DEFAULT 0 CHECK (… >= 0),
    ADD COLUMN failure_threshold  integer NOT NULL DEFAULT 3 CHECK (… BETWEEN 1 AND 10),
    ADD COLUMN recovery_threshold integer NOT NULL DEFAULT 2 CHECK (… BETWEEN 1 AND 10),
    ADD COLUMN status_changed_at timestamptz NOT NULL DEFAULT now();

UPDATE monitors SET status_changed_at = created_at;
```

**Sayaçlar denormalize** (0.1 §5): alternatif, her kontrolde son N
`check_result` satırını okumaktı — kontrol başına fazladan bir zaman serisi
sorgusu.

**Varsayılan 3/2 asimetrik:** kesinti İLAN ETMEK pahalı (yanlış alarm,
gereksiz incident, gece uyanan biri), kesintinin BİTTİĞİNİ söylemek ucuz. Üst
sınır 10: 60 sn aralıklı bir monitor'de 10 ardışık hata, kesintinin 10 dakika
fark edilmemesi demek — daha büyüğü "izleme" olmaktan çıkardı.

**Backfill `created_at`:** mevcut satırlarda durum hiç değişmedi. `now()`
bırakmak, aylardır duran bir monitor'ün durumunun "az önce değişmiş"
görünmesi olurdu.

## 3. Yazma: tek ifade, iki koruma

`db/queries/schedule.sql` → `ApplyCheckOutcome` (3.2'nin `MarkMonitorChecked`'i
bunun içinde eridi):

```sql
UPDATE monitors
SET last_checked_at       = @checked_at,
    current_status        = @status,
    consecutive_failures  = @consecutive_failures,
    consecutive_successes = @consecutive_successes,
    status_changed_at     = CASE WHEN current_status IS DISTINCT FROM @status
                                 THEN @checked_at ELSE status_changed_at END
WHERE id = @id AND is_active;
```

- **TEK İFADE:** sonuç, sayaçlar ve durum aynı yazmada. İki ayrı sorgu olsaydı
  aralarında kalan bir hata, sayacı ilerlemiş ama durumu eski (ya da tersi) bir
  satır bırakırdı.
- **`status_changed_at` yalnızca durum GERÇEKTEN değiştiğinde:** her kontrolde
  tazelenseydi "ne zamandır down?" sorusunun cevabı hep "az önce" olurdu (4.1'in
  incident başlangıcı da buradan türeyecek).
- **`is_active` koşulu bir YARIŞI kapatıyor:** kontrol sürerken kullanıcı
  monitor'ü duraklatmış olabilir; koşul olmasaydı biten kontrol `paused`
  durumunun üzerine `up` yazardı — kullanıcının az önce verdiği kararı ezmek.
  (3.2'nin `ReleaseMonitorClaim`'indeki aynı koruma.)

Ayrıca `UpdateMonitor` (kullanıcının PATCH'i) **aktiflik değiştiğinde sayaçları
sıfırlıyor**: duraklatmadan önce biriken iki ardışık hata, günler sonra devam
ettirilen bir monitor'ü üçüncü hatada DOWN yapmamalı.

## 4. Sözleşme

`monitorResponse` üç yeni okunur alan + iki ayarlanabilir eşik kazandı:

```jsonc
{
  "failureThreshold": 3,     // ayarlanabilir (1-10)
  "recoveryThreshold": 2,    // ayarlanabilir (1-10)
  "status": "down",
  "lastCheckedAt": "2026-08-12T18:00:06.808Z", // null = hiç kontrol edilmedi
  "statusChangedAt": "2026-08-12T17:59:36.823Z"
}
```

**`nextCheckAt` bilinçli olarak YOK:** sıradaki kontrolün zamanı worker'ın iç
defteri, istemcinin kararını değiştirmiyor. `lastCheckedAt` ve
`statusChangedAt` ise kullanıcının gerçekten sorduğu iki soruya karşılık
geliyor ("ölçüm ne kadar taze?", "ne zamandır bu durumda?").

Eşikler `apps/web/src/lib/api-types.ts`'e de eklendi (sözleşme tek yerde
güncelleniyor). **Formda ayar alanı YOK** — bu adım eşiklerin ayarlanabilir
OLMASINI istiyordu; UI'a girmesi monitor formunun kapsamı ve 4.4'ün admin
ekranlarıyla birlikte ele alınacak.

**Gerçek veritabanına karşı:** uçtan uca kesinti + kurtarma (gerçek HTTP
sunucusu bozuluyor/düzeliyor, 7 tur): sayaçların turlar arasında taşındığı,
`status_changed_at`in yalnızca değişimde yazıldığı, kesinti boyunca zaman
serisine yazmanın sürdüğü; monitor bazında eşiklerin (1/1) satırdan okunduğu;
`ApplyCheckOutcome`in duraklatılmış monitor'e dokunmadığı.

**Gerçek konteynerde** (migration `version_id=9`), eşikleri 2/2 olan bir
monitor'le:

| Adım | Sonuç |
| --- | --- |
| Monitor eklendi (`failureThreshold: 2`) | Sözleşmede eşikler görünüyor, `status: pending`, `lastCheckedAt: null` |
| İlk kontrol | `status: up`, `lastCheckedAt` = `statusChangedAt` |
| Hedef bozuldu, 1. hata | `up` kaldı, `consecutive_failures = 1` |
| 2. hata (eşik) | **`down`** + log: `monitor durumu değişti from=up to=down consecutive_failures=2` |
| Hedef düzeldi, 1. kurtarma | Hâlâ `down`, `consecutive_successes = 1` |
| 2. kurtarma (eşik) | **`up`** + log: `from=down to=up consecutive_successes=2` |
| Duraklatma | `paused`, sayaçlar **0'a sıfırlandı**, `next_check_at` NULL |

**Tarayıcıda** (`:3100` → `:3400`): giriş → detay sayfası **"Çalışıyor"**
rozetiyle açıldı, kontrol geçmişindeki satırların hepsi **"zamanlanmış"**
kaynağıyla listelendi (2.3'e kadar yalnızca manuel kontroller vardı), uptime
6 zamanlanmış kontrolden **%66.67** hesaplandı. "Devam ettir" düğmesinden
sonra scheduler monitor'ü 9 saniye içinde kontrol edip `up`a çekti. Hedef
bozulup iki ardışık hata alınca liste **"Kesinti"** rozetine döndü. Ekran
görüntüsü depoda tutulmuyor (0.2'nin kararı), doğrulama DOM'dan yapıldı.

## 6. Sonraki adıma bırakılanlar

- **4.1:** `Transition.Changed` ve `status_changed_at` incident açma/kapama
  için hazır — `up → down` incident açacak, `down → up/degraded` kapatacak.

- **3.4:** toplulaştırma bu adımdan etkilenmiyor (uptime yüzdesi ham
  sonuçlardan hesaplanıyor, durumdan değil) — ama kesinti SÜRESİ hesabı
  `status_changed_at`i kullanabilir.
- **UI:** eşiklerin form alanları ve "3 dakikadır down" gibi gösterimler
  4.4'ün admin ekranlarıyla.
